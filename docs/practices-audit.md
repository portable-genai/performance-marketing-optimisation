| **C1** Identity resolved server-side; client actor/ACL discarded `[all]` **(load-bearing)** | PASS | `api/schemas.py::ReportRequestModel` carries no `actor` field; `api/security.py` resolves a verified `Principal` per route via the `IdentityPort`, and the audit actor is `principal.actor` (the verified subject). `test_api_identity.py` proves an unknown persona is 401 and the recorded actor is the verified subject. The IAP refusal is now split by whose failure it is, and the split is read at the API. In `adapters/gcp/iap_identity.py` the `MKT_PERF_IAP_AUDIENCE` check now runs FIRST, before the assertion header is read, and raises `IapAudienceUnconfiguredError`; the lazy google-auth import moved inside a `try` and raises `IapVerifierUnavailableError`. Both subclass `EndUserAuthUnavailableError` (declared in `ports/identity.py`, carrying `http_status`) and both answer 503, while an absent or blank assertion header stays a plain `IdentityError` and a bare 401 "authentication required" that tells a caller nothing they could forge with. `ctx.header(...)` is now `.strip()`ped, so a header a proxy or a deployment template rendered blank is refused as MISSING instead of reaching the algorithm pin. `api/security.py::get_principal` orders the `EndUserAuthUnavailableError` branch BEFORE the `IdentityError` branch, and the order is load-bearing: it is a subclass, so the reverse silently swallows it and answers the 401 the whole split exists to avoid. `tests/unit/test_iap_refusal_split.py` guards all of it. RED first, offline against the adapter exactly as it shipped: an unset audience with an assertion present gave `IdentityError: MKT_PERF_IAP_AUDIENCE is not configured; cannot verify IAP assertion`, while the operator's bare curl with no header gave `IdentityError: missing IAP assertion header; request did not pass through IAP`, so the deployment fault was reported only to callers who already had an assertion and both answered 401; a `"   "` header gave `IdentityError: assertion is not a compact JWS or JWE, so it carries no readable algorithm header`, a malformed token reported for an absent one; and with the `[gcp]` extra blocked, `ModuleNotFoundError: No module named 'google.auth.transport'` escaped `resolve` and `get_principal` for a bare 500 per request. The new module does not import against that tree at all; with only the two `Iap*Error` types injected and the old behaviour left standing it scored 8 failed / 3 passed, and reordering the two `except` branches on the fixed tree leaves 10 passed and fails `test_the_api_answers_a_deployment_failure_with_its_own_status_and_message` alone, 401 where 503 is owed. The fourth divergence from the `adapters/gcp/identity.py` family, the `principals` tuple, was investigated and deliberately NOT changed: this adapter grants `user:<subject>` and that family grants nothing, and it is this one that agrees with `hex_service_kit.federation.principal_from_iap_claims`, so aligning it would strip a verified identity of its own principal and widen nothing. The divergence is recorded in the test module rather than closed in the wrong direction. **The claim half is the commons decision too (2026-08-26).** `resolve()` no longer constructs a `Principal` at all: everything after the signature check is one `hex_service_kit.federation.principal_from_iap_claims(claims, _FEDERATION_POLICY, source="gcp-iap", include_subject_principal=True)` call, and the cryptography stays in the adapter because the kit's core is pure stdlib with zero runtime dependencies and verifies nothing. `_FEDERATION_POLICY` is a reviewed literal carrying `tenant_from_hosted_domain=True`: this deployment configures no domain map and IAP already restricts the audience to one organisation, so the `hd` claim IS the tenant id here, and that is stated as an OPT-IN rather than left to a fallback. `include_subject_principal` is stated for the same reason: this adapter family grants the verified subject its own `user:<subject>` principal while the `adapters/gcp/identity.py` family does not and the difference is an authorization decision, not a formatting one. `tests/unit/test_iap_claim_half.py` guards it, and it was RED first, offline, in three stages. (1) Against the adapter exactly as it shipped the module would not even import: `ImportError: cannot import name '_FEDERATION_POLICY'`, which is the state in which a load-bearing tenant can be emptied by a default nobody wrote down. (2) With only the policy object added and the hand-rolled tail left standing it scored 4 failed / 6 passed, and those four ARE the finding: the `acr` row and the mixed-case `hd` row of the comparison disagreed, and both `test_a_claim_set_from_another_issuer_cannot_become_a_principal` and `test_a_verified_assertion_that_names_nobody_is_refused` reported `DID NOT RAISE`, because with the claim-set precheck removed the hand-rolled tail read `claims["email"]` and built a verified identity out of a token issued by somebody else. (3) After adoption, 10 passed. Three deliberate defects on the fixed tree keep the guard honest: flipping `include_subject_principal` scores 6 failed / 4 passed, clearing `tenant_from_hosted_domain` fails the passthrough guard, and passing a fresh `FederationPolicy()` at the call site instead of the reviewed one scores 4 failed / 6 passed, on the resolved tenant rather than on an attribute. **Two behaviour changes are recorded rather than normalised away.** `assurance` now prefers an `acr` claim where the shipped tail hardcoded `"iap"`; nothing in this repository reads `Principal.assurance` for an authorization decision, so the change is audit-visible only, and IAP assertions do not carry `acr` in practice. The tenant is now lower-cased where the shipped tail passed `hd` through with only `.strip()`; `principal.tenant` is a partition key, so a mixed-case hosted domain would change the partition, and Google normalises `hd` to lower case in practice. Both were found by EXECUTING the commons against this adapter over the same claim sets, not by reading it. |
